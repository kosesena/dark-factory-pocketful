## Findings (most severe first)

### 1. A hold stays open, keeps funds held and can be captured after its `expires_at`
- Requirement: "An authorization whose `expires_at` is at or before now is `expired` and holds no funds. Reads and writes must reflect expiry…"; capture table: "`expires_at` is at or before now → 409 `authorization_expired`".
- Evidence: `authorizations.py` stores the real deadline as `ts + ttl` (fractional creation instant), but shows `expires_at = int(ts) + ttl`. For up to one second after the shown `expires_at`, the hold is still `open`, `/me` still counts it in `held`, and capture returns 201.
- Reproduction: reset with `authorization_ttl_seconds: 2`. As ada, `POST /authorizations {"to_handle":"bob","amount":100}`. Wait until the wall clock passes the returned `expires_at` by 20 ms. `GET /authorizations` shows `status: "open"`, `GET /me` shows `held` including the 100, and bob's `POST /authorizations/{id}/capture {}` returns **201** and moves money. Expected: `expired`, released, and **409 authorization_expired**. This was observed with ttl 2. With ttl 1 it depends on where in the second the hold was created.

### 2. 5xx on long digit `limit` / `offset` (all list endpoints, including the new `/authorizations`)
- Requirement: §5 "Requests must not produce 5xx responses"; `limit` 1..200 → otherwise 422; `offset` 0 or more.
- Evidence: `GET /activity?limit=` + `9`×5000 → **500 internal_error ValueError**. The same happens on `/requests` and `/authorizations`, and with `offset`. Expected: 422 for `limit`, 200 (empty page) for `offset`. Python's `int()` digit limit is hit in `parse_page`. This is also present in stage-1 a0a5426 (same code; reproduced on 9201). The cross-auditor reported it as F3 against 69289b3.

### 3. Import accepts an invalid state
- Requirement: §10 "an invalid state give[s] 422 `validation_failed` without changing the destination". Responses must carry RFC 3339 timestamps; amount at most 1000000000.
- Reproduction: create one payment, `GET /_test/export`, set `state.payments[0].created_at = "not-a-timestamp"` (or `amount = 1000000001`), `POST /_test/import` → **204**, and the corrupt record is served. Expected 422 with the destination unchanged. This is also present in stage-1 a0a5426 (reproduced on 9201). The cross-auditor reported it as F4.

### 4. UI labels every amount input in the wrong currency outside EUR
- Requirement (stage 2, product direction): "Format people, amounts and timestamps for people first"; "a coherent, presentation-ready consumer finance product".
- Evidence: forms are built before `/me` arrives, from a hard-coded EUR/2 default. In a `JPY`/`minor_units: 0` service, the wallet shows "1200 JPY", but the pay, request and authorise forms say **"Amount (EUR)"** with placeholder "0.00". The split form says "Total you paid (EUR)". See screenshot `home-jpy-1280.png` from `ui_check_s2.py`.
- Reproduction: reset with `{"currency":"JPY","minor_units":0,…}`, log in, open `/`, and read the amount labels.

### 5. Idempotency body equality distinguishes `1.5` from `1.50`
- Requirement: §7 "'Same body' means the same JSON value after parsing".
- Reproduction: `POST /payments` key K body `{"to_handle":"b","amount":1,"x":1.5}` → 201. Repeat K with `"x":1.50` → **409** `idempotency_key_reuse`; expected 200 replay. `_norm` uses `str(Decimal)`, which keeps trailing zeros. Use `Decimal.normalize()` or an equivalent. This is also present in stage-1 a0a5426.
