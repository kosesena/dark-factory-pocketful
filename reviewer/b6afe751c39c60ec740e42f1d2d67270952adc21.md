## Finding 1 (only finding): stripping `view` from a saved statement silently rewrites it
- **Requirements broken:** §10, "an invalid state gives 422 validation_failed without changing the destination". Stage 3, a snapshot "pages that exact result". Stage 4, refunds carry `refund_of` naming the target.
- **Evidence:** `verification/probes_legacy_snapshots.py http://localhost:9504` gives 20 probes, 2 failed:
  - `refund-bearing statement, view removed: imported (204) ... -> refund entry refund_of = ['<absent>']`
  - `refund-bearing statement, all metadata removed: imported (204) ... -> refund entry refund_of = ['<absent>']`
- **Smallest reproduction:**
  1. Reset with users u_a (balance 5000) and u_b (balance 1000), and a seeded payment p_s1 of 300 from u_b to u_a.
  2. Log in as u_a and send `POST /payments/p_s1/refunds {"amount":70}`.
  3. As u_a, `GET /statement` and keep the `snapshot` token. Paging that token shows the refund entry with `"refund_of": "p_s1"`.
  4. `GET /_test/export`, delete `view` from every `state.snapshots[*]`, then `POST /_test/import`. The import returns **204**.
  5. `GET /statement?snapshot=<token>`. The refund entry's payment now has **no `refund_of` key at all**.
- **Why it is invalid:** a snapshot without `view` is treated as a pre-stage-4 statement and pages without `refund_of`. Refunds do not exist before stage 4, so a statement that contains a refund payment cannot be a genuine pre-stage-4 statement. The import must refuse it with 422, or keep paging `refund_of`. This is the stage-4 "del view" fuzz relaxation, and it hides a real fault. The relaxation is only sound when no entry is a refund.
- The fault predates this revision, but earlier passes do not carry over.
