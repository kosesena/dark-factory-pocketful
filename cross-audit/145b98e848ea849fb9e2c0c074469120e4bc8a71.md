| F5 — exact body canonicalization; R047, R048 | §7: “Same body means the same JSON value after parsing”; replay → 200 identical original response; “Same key, different body” → 409 idempotency_key_reuse. | Seed/login a. | F6 — inconsistent imported retry receipt; R085 | §10: “an invalid state give 422 validation_failed without changing the destination”; preserve “all completed idempotent request bodies and original responses.” | Create ordinary payment amount 10 using key p; export. Change only `state.idempotency[0][4].amount` to 999, leaving the original body fingerprint and actual payment unchanged. Import full object → **204**, expected **422 with no state change**. Retry original amount-10 payment/key p → **200 receipt amount 999**, while its referenced payment record remains amount 10. This is demonstrably inconsistent stored state. |

F5 explanation: `common._norm` converts nonintegral or sufficiently large `Decimal` objects to ordinary strings. This preserves spelling differences such as 0.10 vs 0.1 while destroying the distinction between numbers and JSON strings. Small integral examples still normalize successfully, which is why the original minimal reproduction is fixed.

F6 explanation: `snapshot.load_state` validates that the idempotency entry's response is a dictionary, then stores it without verifying receipt shape or consistency with its referenced monetary record.

Both findings were sent immediately to coordinator and implementer. Receipt validation must preserve legitimate historical fields: the original request/split receipt may still say pending and have null payment_id after the current request is paid. Blind comparison against the current mutable resource would break valid exports and replays.
